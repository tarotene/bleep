# ADR-0005 — コード位置とデータ位置を、シェルの構文の構造で決める

- Status: Accepted
- Date: 2026-10-02
- Context: #80(ヒアドキュメント本文の偽陽性・偽陰性)。#79(ADR-0004)の作業中、
  ADR を書くヒアドキュメントの本文にあった `gh` の例が、投稿と誤認されて deny になった
- 関連: ADR-0003(gh の正準形)、ADR-0004(本文ファイルを持つ投稿は単独)

## Context

bleep は、コマンド文字列のうち「シェルが実行しうる部分(コード)」にある `gh` の投稿を
検査する。どこがコードかを、`src/lex.rs` は 2 つの字面の近似で決めていた。

- `split_command_segments` は改行でセグメントに分けるが、ヒアドキュメントを知らない。
  本文の各行を「コマンド」として分類していた
- `substitutions` は「引用符は見ない — 過剰に取る」と、単一引用符の中や
  ヒアドキュメント本文の `$(…)`・バッククォートまで取っていた

その結果、偽陽性(データを投稿と誤認する)と偽陰性(コードを見落とす)の両方が、構造でなく
偶然で決まっていた(再現は #80 の表)。偽陽性は、この repo の作業(ADR・README・Issue 本文に
`gh` の例を書く)で高頻度に出る。README が戒めるとおり、偽陽性の高さは迂回を常態化させる。

## Decision

**シェルが実行しうる文字列を、構文の構造から、コードを運ぶ構文の閉じた一覧による
最小不動点として決める。** 一覧に無いものはデータで、`gh` の投稿を探さない。

コードを運ぶ構文(POSIX 2.7.4 と `sh` の仕様による):

1. トップレベルのコマンド位置(`env`・`timeout` などの前置を飛ばした先)
2. `$(…)`・バッククォート。ただし単一引用符、`$'…'`、`\` で打ち消された `$`・バッククォート、
   引用符付きヒアドキュメントの本文の中を除く。二重引用符の中は展開されるのでコード
3. `sh|bash|zsh|dash|ksh … -c ARG`、`eval ARGS`
4. ヒアドキュメントの本文のうち、次のもの:
   - 標準入力をシェルが読むコマンド(`-c` の無い `sh`・`bash`、`. /dev/stdin`)が同じコマンドに
     あるとき、その本文の全体(`bash <<'EOF'`、`cat <<'EOF' | bash`)。引用符は呼び出し側の
     展開を止めるだけで、受け側の解釈は止めない
   - 置換を含む `eval` の中のヒアドキュメント(`eval "$(cat <<'EOF' … EOF)"`)の本文の全体
   - 引用符なしの区切り(`<<EOF`)の本文中の `$(…)`・バッククォート(本文のその他はデータ)

データ: 上記以外すべて。とくに、引用符付きの区切り(`'EOF'`・`"EOF"`・`\EOF`)の本文でシェルに
流れないもの、単一引用符の文字列、`#` から行末までのコメント。公開する地点(`gh` の投稿の
本文ファイル、`git push` の差分)で照合するので、データの位置を照合する必要は無い
(ADR-0004 の単独のコマンドが、照合したファイルと投稿される中身の一致を保証する)。

### 構造の取り方

- ヒアドキュメント(`<<WORD`・`<<-WORD`)は、本文を「書かれたセグメントの付属物」にする。本文は
  次の改行から WORD だけの行まで。区切りに引用符(`'`・`"`・`\`)が 1 つでもあれば、本文は展開
  されない。`<<-` は終端の行の先頭のタブを無視する
- **曖昧なときは、ヒアドキュメントと見なさない**(続く行を本文と取り違えると、実行される
  コマンドをデータとして見落とす — 取りこぼしの向き)。算術式の中(`$((1<<2))`・`((…))`)、
  here-string(`<<<`)、区切りの語が空・引用符が閉じない、終端の行が無い、のいずれかなら、
  従来どおり本文の行を通常のセグメントとして分ける(過剰側)
- `#` から行末までは、語の先頭にあるとき、コメントとして捨てる(実行も公開もされない)。
  コメントの中の `<<` をヒアドキュメントと取り違える迂回も、これで塞ぐ
- `$'…'`(ANSI-C 引用符)は `\` が直後の 1 文字をエスケープし、`\'` で閉じない。`shell-words` は
  これを知らず、引用符の対応がずれて後ろの語を引用符の中と取り違えるので、語に分ける前に
  同じ字面の単一引用符の語へ直す(`normalize_ansi_c`)
- `--body-file /dev/stdin`・`/dev/fd/N`・`/proc/…`、`..` を含むパスは、PreToolUse の時点で
  中身を読めないので `-` と同じ `body-stdin` として deny する。ヒアドキュメントで本文を
  流し込む形は、構造として解釈でき、この deny に当たる
- `unparsable`(解釈できない)は、引用符が閉じないままの gh の投稿に見える形だけに残る。
  ヒアドキュメント本文のアポストロフィは、もう解釈の失敗を起こさない

### 閉じないもの(不透明な実行)

次は、字面の構文では「コード位置」を決められず、検出のみ(README の「セキュリティ境界では
ない」の範囲)に残る。差分テストが、認識されないことを固定している
(`tests/oracle_test.rs` の `GAPS`)。

- コマンド名を変数で与える形(`f=gh; $f issue …`)
- 標準入力にテキストを流し込む形(`echo '…' | bash`。ヒアドキュメントの本文は読めるが、`echo` の
  引数は読まない)
- python などのインタプリタ、ディスク上のスクリプト、alias
- 深さ 3 を超える入れ子(`sh -c` の中の `sh -c` …)

任意のプログラムが `gh` を呼ぶかどうかは、静的には決定不能である(Rice の定理)。閉じているのは、
透過的な構文で到達できる `gh` だけで、その外は偽陰性を許す。

## 検証: 本物の bash を正解にした差分テスト

`tests/oracle_test.rs` が、PATH の先頭に `gh` のスタブ(引数を記録して終了するだけ)を置き、
コーパスを `bash -c` で実行して、実際に呼ばれた宛先を取る。`bleep-hook intent` の出力と比べる:

- 健全性(全件): 実行された `gh` は、すべて認識される(宛先を取れない `unparsable` の deny も
  認識として数える。素通りではない)
- 精密性(`exact`): 認識された `gh` は、すべて実行される(`||` の短絡や終端の無い
  ヒアドキュメントのような、過剰側の近似を除く)
- 敵対的な組み合わせ: ヒアドキュメントの開始に見える 21 の形と、続く行 8 通りの組み合わせで、
  実行された `gh` が隠れないこと

この差分テストは、実装の途中で、`eval "$(cat <<'EOF' …)"`(二重引用符の中のヒアドキュメントは、
内側で再分割するときに外側の `eval` の文脈を失う)と、`$'<<\'EOF'` の後に閉じない引用符が続く形
(shell-words の ANSI-C 引用符の取り違え)の 2 件の偽陰性を見つけ、直した。

### 検討して採らなかったもの

- **構文木を返すパーサ crate を採用する。** 差分テストが緑になる範囲では、新しい依存は要らない。
  調べた候補(取得 2026-10-02): `yash-syntax` 0.25.0(POSIX 準拠、ヒアドキュメントが AST に入る。
  ただし GPL-3.0-or-later で bleep の MIT と衝突する)、`brush-parser` 0.4.0(ヒアドキュメント
  本文中の置換が AST で返るかとライセンスは未確認)、`tree-sitter-bash` 0.25.1(MIT。
  ヒアドキュメント内の一部の置換を葉として返す取りこぼしが報告されている — 検索結果の要約で、
  原典は未確認。C の依存が増える)。差分テストが、自前の拡張で届かない形を見つけたら、
  そのときに採否を判断する(本命・対抗馬・外した候補つき)
- **データ位置の本文も照合する(従来の過剰な近似)。** 偽陽性の頻度が高く、公開する地点で
  照合する原則(ADR-0004)と重複する。照合しても、プログラムが作る中身は見えない
- **不透明な実行を一律 deny にする。** 日常の操作(`python -c`、スクリプトの実行)まで止まり、
  迂回が常態化する(ADR-0003 と同じ理由)

### 先行研究

- Régis-Gianas, Jeannerod, Treinen, "Morbig: A Static Parser for POSIX Shell", SLE '18, 2018-11,
  <https://hal.science/hal-01890044>(取得 2026-10-02): ヒアドキュメントを含む POSIX シェルの
  静的パーサ。構造を決めてから単純コマンドの語を見る — 本 ADR の「構造から決める」と同じ方向
- Greenberg & Blatt, "Executable Formal Semantics for the POSIX Shell", POPL 2020,
  <https://dl.acm.org/doi/10.1145/3371111>(取得 2026-10-02): 展開を含む形式意味論。実行可能な
  参照実装で、本物のシェルを正解にする差分テストと同じ発想
- The Open Group, "Shell Command Language §2.7.4 Here-Document"
  <https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html>(取得 2026-10-02):
  区切りが引用符付きなら本文は展開されない、引用符なしなら本文の置換が行われる

## 執行点

- `src/lex.rs` — `split_command_segments`(ヒアドキュメント・コメント・ANSI-C 引用符)、
  `substitutions`、`reads_code_from_stdin`、`classify_segment_full`、`normalize_ansi_c`
- `src/grammar.rs` — `is_stream_path`(`/dev/…`・`/proc/…`・`..` を `body-stdin` に)
- `bleep` — `body-stdin` の理由文、selftest(引用符付き本文はデータ、シェルが読む本文は検査)
- `tests/oracle_test.rs` — bash を正解にした差分テスト
- `tests/fixtures/intent/quoted_heredoc_body_is_data.json`
- `tests/fixtures/intent/heredoc_into_shell_is_code.json`

## Consequences

- 本文に `gh` の例を書くヒアドキュメント(`cat > f <<'EOF'`)が、投稿と誤認されなくなる
- `bash <<'EOF'` の本文の `gh` は、偶然でなく構造として検査される
- 引用符なしのヒアドキュメントの本文は、`$(…)`・バッククォートの中だけが検査される
- `unparsable` が出る形が減る。理由文から「ヒアドキュメント」を外した
- `--body-file /dev/stdin <<EOF` は、`unparsable` ではなく `body-stdin` で deny になる
- `LEX_PROTOCOL` は上げない(出力の形式は変わらない。認識の結果が変わるだけ)
