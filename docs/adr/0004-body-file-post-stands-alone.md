# ADR-0004 — 本文ファイルを持つ gh の投稿は、単独のコマンドに限る

- Status: Accepted
- Date: 2026-10-02
- Context: #78(PUBLIC 宛ての Issue 本文に company repo への参照が含まれ、そのまま
  公開された事故)。#78 は、変数で作った本文パスが ask になり中身を見ないまま
  承認された(F1)と、前段が本文ファイルを書き換える TOCTOU(F2)の 2 類型を挙げた
- 関連: ADR-0003 決定 2(gh の正準形)を補う。ADR-0002 提案 2 の「unresolved は ask」は、
  ADR-0003 で置き換え済み

## Context

#78 の F1(シェル変数・`$(…)`・バッククォートで作った本文やパスが
`body-source-unresolved`/`unresolved-var` の ask になり、中身の見えない承認に化ける)は、
ADR-0003(#75)で解消済みである。解決できない形は文法の外として `gh-noncanonical`
の deny になり、ask は出ない。#78 の事故とレッジャーの集計(2026-10-01〜02)は、その前の
版の挙動である。

残る穴は F2 だけである。前段のコピーのあとで本文ファイルを渡す形

```console
$ bleep-hook intent --cwd /tmp -- "cp /tmp/a.md /tmp/x.md && gh issue create -R o/r --body-file /tmp/x.md"
```

は、hook が PreToolUse の時点で `cp` の前の `/tmp/x.md` を読む一方、gh が投稿するのは
`cp` の後の中身である。ADR-0003 の正準形(絶対パスのリテラルのファイル)に入っている
ので、そのまま通る。`>` のリダイレクト、`sed -i`、スクリプトによる書き出しも同じ形に
なる。

公開されるもの(gh が送る本文)と照合されるもの(hook が見るファイル)が別々に作られる
のが根で、両者が一致するかどうかは bash を評価しないと決まらない。

## Decision

**本文ファイルを持つ投稿は、その投稿だけを 1 回のコマンドとして実行する。** 違反は
`gh-noncanonical` の閉じたコード `not-alone` で deny し、理由文は「前段の処理は別の Bash
呼び出しに分ける」ことを案内する。

- 単独とは、コマンド全体がトップレベルのセグメント 1 つで、`env`・`sudo`・`timeout` などの
  前置を除いて `gh` から始まること。`&&`・`;`・`||`・`|`・改行で他のコマンド(`cd`・
  `git push`・他の gh を含む)と並べる形、`sh -c`・`eval`・`$(…)`・バッククォートの
  中の投稿は、単独ではない
- 対象は `body_sources` を持つ投稿だけ。本文ファイルを持たない投稿(`close` など)は
  並べてよい。既に別の違反があれば、それを優先して返す(最初の違反だけを持つ)
- 前段がコマンド文字列に存在しなければ、同じコマンドの中で本文ファイルを書き換える
  ものは無い。「どのセグメントが本文ファイルを書くか」を bash の評価なしに推測する
  代わりに、書けない形にする(ADR-0003 と同じ、認識ではなく構成)
- `LEX_PROTOCOL` を 4 から 5 に上げる(違反コードの語彙が lex の出力の一部のため)

### 検討して採らなかったもの

- **#78 の提案(本文をコマンド文字列内のリテラルに限る — `--body '…'` と `<<'EOF'` の
  ヒアドキュメントだけを正準形にする)。** 照合したものが投稿されるものと字面で同じに
  なり、F1・F2 を構成で閉じる点は、本 ADR と同じ表現不可能性である。採らなかったのは、
  ADR-0003 決定 2 の正準形(本文は絶対パスのファイルだけ。`--body`・stdin は文法の外)と、
  それに乗る運用(本文を Write でファイルにして `--body-file` で渡す。PR テンプレートを
  読ませる規約、tarotene/dotfiles 側の配線)を丸ごと反転させるため。ヒアドキュメント本文
  のアポストロフィでクォートが閉じない形は、現状 `unparsable` で、lex の改修も要る。
  F2 だけを閉じるなら、正準形を反転させなくて済む(2026-10-02 の設計の裁定)
- **隣接する `cd <リテラル>` や `git push` を許す閉じた許可リスト。** `git push` と
  PR 作成を並べる形が通る利点はあるが、許可リストの境界(リダイレクトの検出、pre-push が
  任意の処理をしうること)を維持する必要がある。単独だけにすれば規則が最小で、穴が無い。
  書き直しは Bash 呼び出しを 2 回に分けるだけである(2026-10-02 の設計の裁定)
- **投稿専用の入口(`bleep post` や MCP ツール)を唯一の経路にする。** 照合と投稿を同じ
  プロセスで行うので TOCTOU は起きないが、ADR-0002 が却下した実行時の層とほぼ同じで、
  ホストごとの登録が要る。ADR-0003 も `bleep post` は役割が混ざるとして外している
- **sandbox。** ネットワークやファイルの到達範囲を制限するだけで、本文の中身は照合
  しない。F2 を閉じない

### 閉じないもの

単独のコマンドでも、別プロセスが本文ファイルを書き換える(前の Bash 呼び出しで
バックグラウンド起動したものなど)形は、PreToolUse の字面からは見えない。README の
「セキュリティ境界ではない」の範囲に残る(検出のみ)。単独のコマンド内のリダイレクト
(本文ファイル自身への `>`)は、本文を空にするだけで、照合をすり抜けた中身の公開には
ならない。

## Consequences

- `cd <dir> && …` と `git push && …` を前段にした本文ファイル付きの投稿は deny になる。
  前段を別の Bash 呼び出しに分ければ通る。`-R` が必須なので、`cd` は元から不要である
- 判定レッジャーの `detail` に `not-alone` が増える。消費側の schema
  (tarotene/dotfiles)の閉語彙の拡張が要る
- 複数の投稿を 1 コマンドに並べる形は、本文ファイルを持つなら deny になる。本文を持たない
  `close` などは並べてよい
